**P0 — Dashboard auto-redirects to `/d/jtggz18p2cb6`.**

**P0 — Dev deployment chat returns `401 Missing Authentication header`.**
The Dev bot's thread history shows three consecutive assistant messages that are literally the string `401 Missing Authentication header`. This means the chat backend returned the error body raw to the user rather than sanitizing it. Two issues:
1. Upstream auth header missing on a chat call (likely MCP server / bridge call)
2. Raw error text leaked into the conversation instead of a sanitized user-facing message

**P1 — FIXED — Node orchestration fields silently ignored on load.**
The Zod schema at `jarble-api-main/src/trpc/routers/flows.ts:243` accepts `role`, `goal`, `canDelegate`, `contextScope`, `isEntryPoint` as top-level fields on a FlowNode. The UI saves them nested under `node.config.*`. Server code (`flowDelegation.ts:133`, `flowDelegation.ts:224`, etc.) reads them from the top level (`node.canDelegate`). Result: **every UI-saved flow silently treats `canDelegate` as undefined**, so even when a user unchecks "Can delegate" on a bot, the server still builds delegation tools for it. Symmetric bug in the canvas: `Deployments.tsx:235` only reads from `config.*`, so an API-created flow (top-level fields) renders every node as "Can delegate".

**Fix applied:**
- Added `normalizeFlowNode` and `normalizeFlowDefinition` helpers in `jarble-api-main/src/services/flowEngine.ts:68-113`. They promote `config.{role, goal, canDelegate, contextScope, isEntryPoint, modelOverride}` to top level with top-level values winning when both are set.
- Wired into the three flow read sites in the API: `flowChat.ts:256`, `flowExecution.ts:164`, `tamboAgent.ts:1134`.
- Mirrored the symmetric fix in the UI loader at `Jarble-mvp/views/Deployments.tsx:223` so API-created flows render correctly in the canvas.
- Typecheck clean on both frontend and API. 32 existing `flowDelegation` tests still pass.

### New bugs found in Cycle 2

**P1 — FIXED — Raw `jarble_delegate` block leaks via flowChat else-branch.**
`jarble-api-main/src/routes/flowChat.ts:804` is the fall-through when `delegationTools.length === 0 || delegationCalls.length === 0`. It builds `cleanText` by stripping `<think>/<reasoning>` tags only, then streams the raw text to the user. If the LLM emits a `jarble_delegate` fenced block on its own (e.g. the user typed "delegate this" into a canDelegate=false flow), the block is rendered verbatim in the chat bubble. I reproduced this live:
```
Sure, sending this over to a teammate now!

```jarble_delegate
{ "to": "t3", "task": "What is 2+2?", "context": "" }
```
```
Fix applied at `flowChat.ts:867` — added the same `jarble_delegate` regex strip the `if`-branch uses.

**P1 — FIXED — `jarble_delegate` missing from streaming fence-suppression list.**
`jarble-api-main/src/routes/tamboAgent.ts:1255` has the fence-match regex that strips `jarble_ui`, `jarble_ui_update`, `jarble_ui_define`, `jarble_suggestions`, `jarble_design_context` from the streaming delta. `jarble_delegate` is **not** in the list, so it leaks through per-token streaming in the direct chat path (not just flow chat). Added `delegate` to the regex. Also broadened `stripReasoningTags` at `tamboAgent.ts:323` to strip the block from persisted chat history so it cannot resurface when past conversations are re-rendered.

**P2 — PRE-EXISTING — `better-sqlite3` NODE_MODULE_VERSION ABI mismatch blocks integration tests.**
Running `npx vitest run` hits `Module '...\better_sqlite3.node' was compiled against NODE_MODULE_VERSION 127 but requires 137`. This is a local env issue (Node upgraded, native binding not rebuilt). Blocks 63+ tests that rely on `createTestDb` (SQLite in-memory mirror). Fix is one command: `npm rebuild better-sqlite3`. Not blocking my code changes — the affected tests are pre-existing and fail identically on main.

### Regression guard added

Created `jarble-api-main/src/services/flowEngine.normalize.test.ts` with 10 tests:
1. `config.canDelegate=false` promotes to top level (the exact UI-save shape that Cycle 1 broke on)
2. All six orchestration fields promote (role/goal/canDelegate/contextScope/isEntryPoint/modelOverride)
3. Top-level wins when both sides set the same field (most explicit wins)
4. Leaves top-level alone when config is missing (API-created flows)
5. Idempotent (normalize twice == normalize once)
6. Undefined when neither location defines a field
7. `normalizeFlowDefinition` walks every node
8. Leaves edges alone
9. Safe on empty/malformed input (`[]`, `{}`, `null`)
10. **Integration:** `buildDelegationTools` returns `[]` after normalization when `config.canDelegate=false` — proves the end-to-end chain works

Also had to mock `db/index.js` + `logger.js` because `flowEngine.ts` transitively imports `db` which throws without `DATABASE_URL`. Ran cleanly after adding `vi.mock` for both modules.

### Narrowed the return type of `normalizeFlowNode`

First pass signature (`<T extends Partial<FlowNode>> (node: T): T`) narrowed too tightly — the input literal didn't include the promoted fields, so `out.canDelegate` tripped `TS2339` in the tests. Fixed by returning `T & Pick<FlowNode, 'role' | 'goal' | 'canDelegate' | 'contextScope' | 'isEntryPoint' | 'modelOverride'>`. Typecheck clean on both frontend and API after the change.

## Cycle 3 — Pipeline topology chained execution

**Status:** ✅ Pipeline execution + priorContext chaining VERIFIED live. 1 P1 bug found + FIXED (template `.result` alias). 4 new unit tests added.

### Architecture finding — `teamType` is cosmetic

Greped `teamType` / `pipeline` across the entire server tree (`flowChat.ts`, `flowDelegation.ts`, `flowEngine.ts`, `tamboAgent.ts`, schema, routers): the field is stored in `orchestration_flows.team_type` and round-tripped through CRUD, but **never read by any server code path**. It's purely a UI layout hint consumed by `Deployments.tsx:420` which picks a dagre direction (`LR` for pipeline, `TB` for hierarchy, circular for collaborative). "Pipeline semantics" come entirely from (a) user-arranged edges and (b) `flowEngine.executeDeploymentViaDelegation` topological execution. Worth documenting because every team member asking "how does pipeline differ from hierarchy on the server?" will get the same confused answer.

### End-to-end finding — priorContext auto-chain works

Stage 2 successfully received "blue" from stage 1 and reversed it to "eulb" — **even though the template `{{stage1.result.response}}` silently returned empty string**. The data reached stage 2 via `buildPriorStepContext` which walks incoming edges and appends `[Label]: JSON.stringify(result)` to the delegation call's `context` field. The downstream bot parsed the color from the context rather than from the task literal. Good news: delegation context is a real safety net. Bad news: the bot is doing implicit work to recover from the template failure, and stage 3 proved the safety net has limits.

### P1 — FIXED — Template `{{nodeId.result.field}}` silently returned empty

**Repro:** stage 3's `config.task` was `"Stage1 picked: {{stage1.result.response}}. Stage2 reversed: {{stage2.result.response}}."`. Its actual LLM output:

> "The pipeline ran in two stages: **Stage 1** picked an empty value, and **Stage 2** reversed it — resulting in no meaningful output."

Both templates silently resolved to empty string. The LLM followed the literal task text ("picked: . reversed: .") and invented an "empty value" narrative, even though `priorContext` contained both real results.

**Root cause:** `flowEngine.ts:1307` at `resolveTemplatePath` initializes `current = stepResult.result` (the unwrapped value), then walks the remaining path parts. For `{{stage1.result.response}}`:
- parts = `["stage1", "result", "response"]`
- current starts as `{ response: "blue", uiBlocks: [], ... }` (the unwrapped deployment result)
- i=1: `current["result"]` → `undefined` (no `result` key on the unwrapped shape)
- i=2: current is undefined → return undefined → substitute `""`

Users coming from JavaScript object access will write `{{nodeId.result.field}}` every time — `stepResult.result.response` feels natural. The docstring on line 12 only showed the positional alias `{{stepN_result.field}}` (a single token), not the recommended direct form `{{nodeId.field}}`. **I myself hit this bug writing the Cycle 3 test**, which is the clearest signal that the naming trips people up.

**Fix:** `flowEngine.ts:1283` now accepts three equivalent forms:
1. `{{nodeId.field}}` — direct (recommended)
2. `{{nodeId.result.field}}` — alias (matches JS intuition)
3. `{{stepN_result.field}}` — positional

The alias is narrow: if the next path segment is literally `"result"` AND the current object does **not** have its own `result` key, the walker treats it as a no-op. This means transform nodes that legitimately return `{ result: "x", other: "y" }` still get `{{transform1.result}}` reading the inner key — the alias never masks a real field access. Regression pinned by a test called *does NOT hijack .result when the result object has its own result key*.

Also updated the file header docstring at `flowEngine.ts:12` to show all three forms so the next person reading the source sees the canonical surface area immediately.

### Events NOT emitted during Cycle 3 test

The SSE reconnect returned a snapshot mid-execution, so `step.started` events for `stage1` were already past when I connected. Only `stage2` and `stage3` started events appeared in the live stream. This is expected SSE reconnect behavior — the snapshot captures "already running" but doesn't replay historic step events. If you need full event history on reconnect, you'd need to connect before starting or add a replay buffer to `attachEngineToSSE`. Not a bug, but worth noting for future QA.
