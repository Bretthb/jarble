### P1 — FIXED — Template `{{nodeId.result.field}}` silently returned empty

**Repro:** stage 3's `config.task` was `"Stage1 picked: {{stage1.result.response}}. Stage2 reversed: {{stage2.result.response}}."`. Its actual LLM output:

> "The pipeline ran in two stages: **Stage 1** picked an empty value, and **Stage 2** reversed it — resulting in no meaningful output."

Both templates silently resolved to empty string. The LLM followed the literal task text ("picked: . reversed: .") and invented an "empty value" narrative, even though `priorContext` contained both real results.

**Root cause:** `flowEngine.ts:1307` at `resolveTemplatePath` initializes `current = stepResult.result` (the unwrapped value), then walks the remaining path parts. For `{{stage1.result.response}}`:
- parts = `["stage1", "result", "response"]`
- current starts as `{ response: "blue", uiBlocks: [], ... }` (the unwrapped deployment result)
- i=1: `current["result"]` → `undefined` (no `result` key on the unwrapped shape)
- i=2: current is undefined → return undefined → substitute `""`

Users coming from JavaScript object access will write `{{nodeId.result.field}}` every time — `stepResult.result.response` feels natural. The docstring on line 12 only showed the positional alias `{{stepN_result.field}}` (a single token), not the recommended direct form `{{nodeId.field}}`. **I myself hit this bug writing the Cycle 3 test**, which is the clearest signal that the naming trips people up.

**Fix:** `flowEngine.ts:1283` now accepts three equivalent forms:
1. `{{nodeId.field}}` — direct (recommended)
2. `{{nodeId.result.field}}` — alias (matches JS intuition)
3. `{{stepN_result.field}}` — positional

The alias is narrow: if the next path segment is literally `"result"` AND the current object does **not** have its own `result` key, the walker treats it as a no-op. This means transform nodes that legitimately return `{ result: "x", other: "y" }` still get `{{transform1.result}}` reading the inner key — the alias never masks a real field access. Regression pinned by a test called *does NOT hijack .result when the result object has its own result key*.

Also updated the file header docstring at `flowEngine.ts:12` to show all three forms so the next person reading the source sees the canonical surface area immediately.

## Cycle 5 — Reports topology upward reporting

**Status:** ✅ 10 new unit tests + bidirectional live verification in prod. **1 UX/docs finding documented** (not code-fixed). 0 functional bugs.

### The big architectural finding

**`reports` and `collaborates` are behaviorally identical in `buildDelegationTools`.** The filter at `flowDelegation.ts:144-156` has three matching branches:

```ts
(e.source === node.id && (et === "delegates" || et === "reports" || !et)) ||  // 149
(et === "reports" && e.target === node.id) ||                                  // 151
(et === "collaborates" && (e.source === node.id || e.target === node.id))     // 153
```

For a `reports` edge A→B:
- Node A matches line 149 → target = B (normal direction). Reporter gets tool to manager.
- Node B matches line 151 → target = edge.source = A (flipped). Manager gets tool to reporter.

For a `collaborates` edge A→B the same two tools are built (via line 153 twice). **Both edge types yield the exact same {A→B, B→A} tool pair.** The only difference is cosmetic:
- `reports` → amber dashed line + "reports" label (`Deployments.tsx:1265, 1282`)
- `collaborates` → violet solid line + "collaborates" label (`Deployments.tsx:1266, 1283`)

The docstring at `flowDelegation.ts:138` even says `"reports": one-way, source reports to target — target can delegate down, source can send up`. So the author knew: the edge is visually one-way but delegation-wise two-way.

### Cycle 5 Finding (DOCS/UX — not code-fixed)

**Users drawing a `reports` edge will assume one-way delegation based on the visual.** A dashed directional arrow strongly implies "information flows in one direction only". The engine does NOT enforce this — both ends can initiate delegation. For example, in a flow where junior reports to senior:
- Junior (reporter) CAN call senior via `{"to": "senior"}` (upward reporting, matches expectation)
- Senior (manager) CAN call junior via `{"to": "junior"}` (downward delegation, **may surprise users** who think "reports" means the arrow locks direction)

**Why this matters:** if a builder wants strict one-way delegation (e.g., read-only audit bot that reports findings upward but must never be called), `reports` does NOT provide that. They would need `delegates` (which IS one-way: line 149 only matches when `e.source === node.id`) and accept the visual language being "delegates" instead of "reports".

**Not code-fixed in Cycle 5** because changing the semantics would break existing flows relying on the bidirectional behavior, and changing the UI visual would need design input. Logged as a documentation / UX gap. Recommended follow-ups:
1. Add hover tooltip on `reports` edges: "Bidirectional — manager can also delegate tasks down to the reporter"
2. Update any user-facing docs that imply reports is one-way
3. Consider adding a `reports_strict` edge type (or a per-edge `bidirectional: false` flag) for users who want strict org-chart enforcement

## Cycle 6 — Delegation depth limit enforcement

**Status:** ✅ Refactor + 12 regression tests. 0 new bugs. The depth enforcement is genuinely solid.

### Architecture finding (benign) — two call sites, same arithmetic

Before this cycle the depth check lived as inline `depth > MAX_DELEGATION_DEPTH` expressions at two places in `flowDelegation.ts`:

1. **Top-level throw path** at line 664-667 inside `executeDelegation` — rejects the call with `DelegationDepthExceededError` before any DB work.
2. **Sub-delegation graceful-refusal path** at line 1058-1066 inside the recursive child-delegation loop — when a child bot wants to recurse one level deeper and the next hop would bust the limit, it appends `[sub-delegation to X refused: depth N > max M]` as an annotation on the parent response instead of throwing. Keeps the parent's reply usable.

Both sites use strict `>` (not `>=`), so with `MAX_DELEGATION_DEPTH = 4` the chain can reach depths `0..4` (entry + four hops) and depth `5` is the first rejected value. depth=0 is "entry bot before any delegation hop" and is always allowed.

### Refactor: extract pure helpers

To make the depth enforcement testable without DB/exec mocks, I extracted two pure helpers into the service:

```ts
export function wouldExceedDepth(depth: number): boolean {
  return depth > MAX_DELEGATION_DEPTH;
}
export function enforceDelegationDepth(depth: number): void {
  if (wouldExceedDepth(depth)) throw new DelegationDepthExceededError(depth);
}
```

Both call sites updated:

## Cycle 7 — Cycle detection in delegation

**Status:** ✅ Refactor + 15 unit tests. 0 functional bugs. 1 minor defensive improvement (defensive array copy on error payload).

### Refactor: pure helpers

Extracted two helpers mirroring the Cycle 6 depth helpers:

```ts
export function wouldCreateCycle(
  ancestors: readonly string[],
  targetDeploymentId: string,
): boolean {
  return ancestors.includes(targetDeploymentId);
}

export function enforceNoCycle(
  ancestors: readonly string[],
  targetDeploymentId: string,
): void {
  if (wouldCreateCycle(ancestors, targetDeploymentId)) {
    throw new DelegationCycleError([...ancestors], targetDeploymentId);
  }
}
```

Both call sites updated:
- `executeDelegation` now calls `enforceNoCycle(ancestors, params.targetDeploymentId)` at line 669
- Sub-delegation path now calls `wouldCreateCycle(nextAncestors, tool.targetDeploymentId)` at line 1049

### Defensive improvement — error payload is now a snapshot

The old code passed `ancestors` directly into the `DelegationCycleError` constructor, which stored a reference (not a copy). In practice no caller mutated the ancestors array after throwing, so this was a dormant footgun. The new `enforceNoCycle` explicitly does `[...ancestors]` so the error payload is a point-in-time snapshot. Pinned by a test called *enforceNoCycle snapshots the ancestors list (mutating it later is safe)* which mutates the caller's array after the throw and asserts the error's `.chain` stays intact.

This is a zero-risk defensive improvement. If a future change introduces a mutable ancestors pattern, the error payload stays correct.

### Documented architectural constraint

**Cycle detection uses `deploymentId`, not `nodeId`.** If a user wires the same deployment into two different nodes of a flow graph (e.g., `nodeA=Generator` running t1, `nodeC=Reviewer` also running t1), the second hop looks like a cycle even if the nodes have different roles and goals. This is intentional — one pod is one LLM conversation, so calling the same deployment twice in the same chain is blocked regardless of role attribution. Test #15 pins this with a clear comment so anyone investigating a "why did my flow trigger a cycle?" bug has a direct link to the constraint.

Practical implication: if you need the same model/config acting in two different roles in a pipeline, you need two separate *deployments* (duplicate the bot), not two flow *nodes* pointing at the same deployment.

## Cycle 8 — Error sanitization through delegation

**Status:** ✅ Extracted hardened `sanitizeDelegationError` pure helper. **4 concrete leak sites found, 3 fixed, 1 was dead code.** 25 new tests covering every regex rule + realistic compound payloads.

### The audit

The existing inline sanitizer at `flowChat.ts:666-673` had six regex rules against exec wrappers, trace/session env vars, and CLI flags. But auditing the surrounding code for **every** place raw error text could reach a user surfaced:

**Leak site A — `flowChat.ts:666-673` is dead code.**
The inline sanitizer is assigned to a local `sanitizedError` variable that is **never used**. The `delta` actually sent to the user is a hardcoded generic `"*Delegation to X was unsuccessful. The team member may be busy or temporarily unavailable.*"`. So the whole delegation-failure user-text path was already safe — just by accident, via a refactor that dropped the reference but left the regex chain behind as cargo.

**Leak site B — `flowChat.ts:525` raw `errMsg` in entry-bot failure.**
```ts
delta: `Sorry, I couldn't reach the entry bot. Error: ${errMsg}`
```
When `chatViaExec` throws (timeout, ENOTFOUND, pod restart, bad auth), `errMsg` contains whatever the underlying exec wrote — commonly the full shell command including `--session-id`, `--timeout`, and the user's literal `--message`. **Unsanitized**. Real leak.

**Leak site C — `flowChat.ts:639` raw `delegationError` in the `jarble.flow.delegation.end` CUSTOM event's `error` field.**
```ts
sendEvent(res, { type: CUSTOM, name: "jarble.flow.delegation.end",
  value: { ..., error: delegationError, ... } });
```
The frontend can render this field (error toast, detail panel, error popover). Same raw content as leak site B — wire-level leak channel.

**Leak site D — `flowChat.ts:646` raw `delegationError` in `delegationTrace.push(...)`.**
The trace is then re-emitted at `flowChat.ts:890-902` via `jarble.flow.chat.trace`. Second wire channel for the same raw content.

### The hardened helper

Extracted `sanitizeDelegationError(raw: unknown): string` in `flowDelegation.ts` — pure, no I/O, idempotent. Strips **beyond** the old inline rules:

| Category | Old rules | Cycle 8 rules |
|---|---|---|
| Exec wrapper | `error executing command [...]` | same |
| Trace env vars | `TRACEPARENT=`, `JARBLE_CURRENT_SESSION_ID=` | same |
| CLI flags | `--session-id`, `--timeout`, `npx openclaw agent --message` | **+ `--user-id`** (both space and equals forms), **+ `--thinking`**, both space and equals forms for all |
| API keys | none | **+ `sk-ant-*`**, **+ `sk-or-*`**, **+ generic `sk-*` ≥ 20 chars** |
| Env var assignments | none | **+ `ANTHROPIC_API_KEY=`**, **+ `OPENROUTER_API_KEY=`**, **+ `OPENAI_API_KEY=`** |
| Length cap | none | **+ 300 char cap with ellipsis** |
| Input types | string only | **+ Error objects, + arbitrary values via String coercion** |
| Fallback | `"an internal error occurred"` | same, plus **`"execution error"`** intermediate label for pure-exec-garbage |

**Critical ordering discovery:** env var stripping MUST run before bare API key stripping. I wrote the tests first with the naive ordering (`sk-ant-*` first), and the *compound multi-leak* test caught it: bare keys were stripped first, leaving `ANTHROPIC_API_KEY=[redacted api key]`, then the env var regex partially consumed the replacement leaving a dangling `api key]` fragment. Reordered to strip env vars atomically first. **Found by a test I thought would pass.** Best argument for writing the test battery before claiming the sanitizer works.

### Four fix sites

1. **Site B — entry-bot failure** (`flowChat.ts:525`): wrapped `errMsg` in `sanitizeDelegationError(...)` before appending to the user's delta.
2. **Site C — delegation.end event error field** (`flowChat.ts:639`): compute `safeDelegationError = delegationError ? sanitizeDelegationError(delegationError) : null` at the top of the result-processing loop, use in the CUSTOM event payload.

4. **Site A — dead sanitizer** (`flowChat.ts:665-673`): replaced the 7-line inline regex chain with a 3-line comment explaining that the user-visible delta stays generic and technical users can check `delegation.end.value.error` for the sanitized detail. ### P2 — FIXED — Synthesis prompt sees empty body when specialist produces only blocks

**Root cause found at `flowChat.ts:716`.** The synthesis prompt is built from `delegationTrace.filter((d) => d.success).map((d) => "[BEGIN ${slug} FULL REPLY]\n${d.fullResponse}\n[END ${slug} FULL REPLY]")`. `d.fullResponse` is the parsed text from the specialist — when a specialist emits `jarble_ui` blocks with **no preamble text**, `fullResponse` is empty and the synthesis prompt becomes:

### P2 UX/security finding — bots see `[DELEGATION_CONTEXT]` wrapper and flag it as prompt injection

Discovered while trying to force the blocks-only path. The second test's specialist reply started:

> "I notice something important here that I want to be transparent about. The `[DELEGATION_CONTEXT]` block in your message — along with content injected into `SOUL.md` — appears to be a..."

(183 chars, truncated mid-sentence in the capture but clearly heading toward "prompt injection attempt")

**Root cause at `flowDelegation.ts:887`**: the delegation wrapper is literally injected into the user message:

```ts
message = `[CANVAS_STATE]\nNo cards on canvas.\n[/CANVAS_STATE]\n[DELEGATION_CONTEXT]\nYou are being delegated a task by a coordinator bot. Render your response as jarble_ui components.\n...rules...\n[/DELEGATION_CONTEXT]\n${message}`;
```

The specialist bot sees this wrapper as raw input and a cautious model correctly flags it as "wait, something is injecting content into my context". It then refuses to use `render_ui` — even though the tool IS available — and instead writes a polite "I can't do this because the environment looks suspicious" refusal. **The first test worked because the user prompt didn't set off the model's injection-detection heuristics.** The second test's aggressive "DO NOT write ANY text" phrasing matched patterns the model is trained to resist.

**Why this is a finding and not a bug**: the wrapper does its job — the FIRST test specialist happily followed the rendering rules. But the wrapper is FRAGILE:
- Chatty models can expose the internal plumbing to users by quoting it
- Aggressive task phrasing triggers refusal behavior
- Future model updates might make more models flag it
- Users see cryptic "I notice [DELEGATION_CONTEXT]..." responses without knowing what's happening

**Recommended follow-ups (not code-fixed this cycle)**:
1. Move delegation rules into a proper **system prompt** via OpenClaw / MCP protocol rather than wrapping the user turn. Most LLMs trust system-role instructions and don't surface them to users.
2. Or rename the wrapper to a tag name LLMs don't associate with injection patterns (e.g., `<flow_rules>` instead of `[DELEGATION_CONTEXT]` which sounds like a user-facing term).
3. Add a log-metric that counts specialist replies containing literal `[DELEGATION_CONTEXT]` so the pattern is monitored.

Logged in the running report. This is a medium-priority improvement but blocking it on Cycle 9 would force a multi-file refactor of the delegation/exec path.

## Cycle 10 — Active team selection persistence

**Status:** ✅ **2 P1 stale-reference bugs FOUND and FIXED**, both reproduced live in prod against the pre-fix code, typecheck clean. No new unit tests (mutations hit DB heavily; fix validated via live API reproduction).

### The two bugs

`deployments.activeFlowId` is a plain `varchar(255)` column at `schema.pg.ts:94` with **no foreign key** to `orchestration_flows.id`. That's a fine schema choice but it means writes to the flow table need to explicitly clean up dangling references. Neither of the two flow-mutating paths did.

**Bug 1 — `flows.delete` leaves stale activeFlowId.** Both hard delete (`db.delete(orchestrationFlows)`) and soft delete (archive + strip memberships) update the flow row and the join table but never touch `deployments.activeFlowId`. **Bug 2 — `flows.update` leaves stale activeFlowId on removed members.** When a user edits a flow to drop a node, `syncFlowMemberships` wipes and re-inserts the `flow_deployment_memberships` rows. The removed deployment's membership row is gone, but its `activeFlowId` still points at the flow it was just removed from.

### Silent runtime consequence

At `tamboAgent.ts:1118-1121`:
```ts
const activeFlowId = deployment.activeFlowId;
const membership = (activeFlowId
  ? memberships.find((m) => m.flowId === activeFlowId)
```

When `activeFlowId` is stale, `find(...)` returns `undefined` and the `||` falls through to `memberships[0]` — whichever team happens to be first in the user's membership list. **Silent mis-routing**: the UI can show "active team: Engineering Squad" while the bot actually delegates via "Marketing Squad". Breaks the contract that `setActiveFlow` persists a specific choice.

## Cycle 11 — Team Chat panel in canvas

**Status:** ✅ **3 duplicate regex sites consolidated + 3 holes plugged** in a shared helper. 24 new frontend unit tests. Typecheck clean.

### The audit

The Team Chat panel in the Bot Teams canvas renders inline chat bubbles via the raw `msg.content` string. I traced the code and found **three separate inline delegation-block transform implementations** in the frontend, each with the same regex pattern and the same three latent bugs:

1. `Jarble-mvp/components/MarkdownMessage.tsx:10-23` — per-deployment chat (blockquote format)
2. `Jarble-mvp/views/Deployments.tsx:4069-4072` — Team Chat panel in canvas (inline format)
3. `Jarble-mvp/components/workspace/ConversationHistoryPanel.tsx:34-40` — sidebar preview (strip entirely)

All three used variants of:
```ts
.replace(/```jarble_delegate\s*\n\s*\{[^}]*"to"\s*:\s*"([^"]+)"[^}]*"task"\s*:\s*"([^"]*)"[^}]*\}\s*\n?```/g, ...)
```

### The three holes in the old regex

**Hole 1 — field order dependency**: the regex requires `"to"` to appear before `"task"`. LLMs **do not** guarantee JSON field order. If the specialist emits `{"task":"...","to":"..."}`, the match fails and the raw fenced JSON leaks to the user. I caught this exact pattern in live testing during Cycles 4–9 on intermittent turns.

**Hole 2 — braces inside the task string**: `[^}]*` between fields cannot match `}`, so a task containing `"render {foo: bar} as a card"` breaks the match. Any bot asked to produce code/JSON snippets via delegation is a candidate for this failure mode.

**Hole 3 — escaped quotes inside the task string**: `"([^"]*)"` stops at the first literal `"`, so a task containing `"Say \"hello\" in French"` breaks the match. Escaped quotes are common in natural-language tasks.

All three holes have the same failure signature: **the raw fenced JSON leaks verbatim into the user's chat bubble**. The per-turn probability is low (LLMs often happen to use "to" first and keep tasks brace-free), but it's non-zero and degrades trust.

### Fix — shared helper using proper JSON parsing

Created `Jarble-mvp/lib/delegationBlockTransform.ts` with three exported functions:

| Export | Purpose |
|---|---|
| `parseDelegationBody(body: string)` | `JSON.parse` the fenced body and return `{to, task, context?}` or null. Handles both `{to, task}` and legacy `{tool: "delegate_to_X", task}` formats. |
| `transformDelegationBlocks(text, {format, maxTaskChars})` | Replace each fenced block with human-readable text. `format: "blockquote"` (Markdown `>`) or `"inline"` (plain). Malformed blocks are silently stripped (never leaked). |
| `stripDelegationBlocks(text)` | Replace each fenced block with empty string. Used by the conversation sidebar where delegation mechanics shouldn't appear at all. |

The key change: the outer-fence regex captures only `` ```jarble_delegate\n(.*?)\n``` ``, and then the body is **parsed as JSON** rather than extracted via regex. Field order is irrelevant. Braces and escaped quotes work. The fail-safe is "strip silently" rather than "leak raw" — users still see delegation status pills via `delegation.start/end` SSE events on a separate channel, so nothing is actually lost.

### Three call sites updated

- **`MarkdownMessage.tsx:10-23`** (24 lines) → `import { transformDelegationBlocks }` + call with `format: "blockquote"`. Net delta: -13 lines.
- **`Deployments.tsx:4069-4072`** (4 lines) → `import` + call with `format: "inline", maxTaskChars: 100`. Net delta: -2 lines.
- **`ConversationHistoryPanel.tsx:34-40`** (7 lines) → `import { stripDelegationBlocks }` + compose with the existing `CANVAS_STATE`/`DELEGATION_CONTEXT` tag strip. Net delta: ~0 lines, stripping now handles legacy + reversed-order blocks.

**Single source of truth** — the next delegation-format change only needs to update the helper.

For fast-failing or synchronous-fast executions, the client's GET `/stream` connection lands AFTER the engine has already finished.   res.end();
```ts
  releaseConnection(user.id);
```

This is **correct behavior** — you don't want to replay every historic `step.started`/`step.finished` event from a completed execution. The snapshot contains all the data a client needs to reconstruct the final timeline (per-step status + error + durations). The frontend's `useFlowExecution` hook can render the full state from the snapshot alone without needing live step events.

**Gap**: the snapshot's `stepResults` is keyed by nodeId but does NOT include the `label` field from the flow definition. The frontend has to join snapshot data with the cached flow definition to render human-readable step names. Not a bug because the frontend already has the definition loaded, but worth documenting.
