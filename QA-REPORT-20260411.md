### Architecture findings (no bug, worth logging)

1. **`teamType` is purely cosmetic.** Greped the full server tree (Cycle 3): the field is stored in `orchestration_flows.team_type` and round-tripped through CRUD, but **never read** by any server code path. Pipeline/hierarchy/collaborative semantics come entirely from how users arrange edges + `flowEngine` topological execution. It's consumed only by `Deployments.tsx:420` to pick a dagre layout direction. Worth documenting so the next person asking "how does pipeline differ from hierarchy on the server?" gets the right answer.

2. **`reports` ≡ `collaborates` in `buildDelegationTools`.** Both edge types produce mutual `{A→B, B→A}` tool pairs. The only difference is visual (amber dashed vs violet solid). See bug #18 above.

3. **Cycle detection matches on `deploymentId`, not `nodeId`.** If you wire the same deployment into two different nodes (e.g. `nodeA=Generator` + `nodeC=Reviewer` both running t1), the second hop is treated as a cycle. **Intentional constraint** — one pod is one LLM conversation, so calling it twice in the same chain is blocked regardless of role attribution. Pinned by a Cycle 7 test with a clear comment so future debuggers have a direct link.

4. **Session lock Map is per-API-pod.** Documented in the new `sessionLock.ts` helper's docstring. Works today on the single-replica Kubero deployment; horizontal scaling for flow chat would need a Redis-backed distributed lock. Flagged for the post-marathon architecture backlog.

5. **SSE reconnect semantics for terminal executions.** Fast-failing or synchronous-fast executions finish before the client's GET `/stream` connects. `flowExecution.ts:475-482` correctly sends a snapshot-then-end in that case — replaying historic events would be wasteful and the snapshot contains all the step-result data needed to reconstruct the final timeline. Re-affirmed twice (Cycles 12 and 14). **Correct behavior, not a bug**, but worth documenting so future debuggers don't chase a phantom "missing events" bug.

6. **Subflow nesting depth limit is 3 levels.** Plus a cumulative `MAX_TOTAL_NODES = 100` budget that prevents subflow amplification attacks. Both verified live in Cycle 14.

**P0 — Dashboard auto-redirects to `/d/jtggz18p2cb6`.**

**P0 — Dev deployment chat returns `401 Missing Authentication header`.**
The Dev bot's thread history shows three consecutive assistant messages that are literally the string `401 Missing Authentication header`. This means the chat backend returned the error body raw to the user rather than sanitizing it. Two issues:
1. Upstream auth header missing on a chat call (likely MCP server / bridge call)
2. Raw error text leaked into the conversation instead of a sanitized user-facing message

**P1 — FIXED — Node orchestration fields silently ignored on load.**
The Zod schema at `jarble-api-main/src/trpc/routers/flows.ts:243` accepts `role`, `goal`, `canDelegate`, `contextScope`, `isEntryPoint` as top-level fields on a FlowNode. The UI saves them nested under `node.config.*`. Server code (`flowDelegation.ts:133`, `flowDelegation.ts:224`, etc.) reads them from the top level (`node.canDelegate`). Result: **every UI-saved flow silently treats `canDelegate` as undefined**, so even when a user unchecks "Can delegate" on a bot, the server still builds delegation tools for it. Symmetric bug in the canvas: `Deployments.tsx:235` only reads from `config.*`, so an API-created flow (top-level fields) renders every node as "Can delegate".

**Fix applied:**
- Added `normalizeFlowNode` and `normalizeFlowDefinition` helpers in `jarble-api-main/src/services/flowEngine.ts:68-113`. They promote `config.{role, goal, canDelegate, contextScope, isEntryPoint, modelOverride}` to top level with top-level values winning when both are set.
- Wired into the three flow read sites in the API: `flowChat.ts:256`, `flowExecution.ts:164`, `tamboAgent.ts:1134`.
- Mirrored the symmetric fix in the UI loader at `Jarble-mvp/views/Deployments.tsx:223` so API-created flows render correctly in the canvas.
- Typecheck clean on both frontend and API. 32 existing `flowDelegation` tests still pass.

## Cycle 5 — Reports topology upward reporting

**Status:** ✅ 10 new unit tests + bidirectional live verification in prod. **1 UX/docs finding documented** (not code-fixed). 0 functional bugs.

### The big architectural finding

**`reports` and `collaborates` are behaviorally identical in `buildDelegationTools`.** The filter at `flowDelegation.ts:144-156` has three matching branches:

```ts
(e.source === node.id && (et === "delegates" || et === "reports" || !et)) ||  // 149
(et === "reports" && e.target === node.id) ||                                  // 151
(et === "collaborates" && (e.source === node.id || e.target === node.id))     // 153
```

For a `reports` edge A→B:
- Node A matches line 149 → target = B (normal direction). Reporter gets tool to manager.
- Node B matches line 151 → target = edge.source = A (flipped). Manager gets tool to reporter.

For a `collaborates` edge A→B the same two tools are built (via line 153 twice). **Both edge types yield the exact same {A→B, B→A} tool pair.** The only difference is cosmetic:
- `reports` → amber dashed line + "reports" label (`Deployments.tsx:1265, 1282`)
- `collaborates` → violet solid line + "collaborates" label (`Deployments.tsx:1266, 1283`)

The docstring at `flowDelegation.ts:138` even says `"reports": one-way, source reports to target — target can delegate down, source can send up`. So the author knew: the edge is visually one-way but delegation-wise two-way.

### Cycle 5 Finding (DOCS/UX — not code-fixed)

**Users drawing a `reports` edge will assume one-way delegation based on the visual.** A dashed directional arrow strongly implies "information flows in one direction only". The engine does NOT enforce this — both ends can initiate delegation. For example, in a flow where junior reports to senior:
- Junior (reporter) CAN call senior via `{"to": "senior"}` (upward reporting, matches expectation)
- Senior (manager) CAN call junior via `{"to": "junior"}` (downward delegation, **may surprise users** who think "reports" means the arrow locks direction)

**Why this matters:** if a builder wants strict one-way delegation (e.g., read-only audit bot that reports findings upward but must never be called), `reports` does NOT provide that. They would need `delegates` (which IS one-way: line 149 only matches when `e.source === node.id`) and accept the visual language being "delegates" instead of "reports".

**Not code-fixed in Cycle 5** because changing the semantics would break existing flows relying on the bidirectional behavior, and changing the UI visual would need design input. Logged as a documentation / UX gap. Recommended follow-ups:
1. Add hover tooltip on `reports` edges: "Bidirectional — manager can also delegate tasks down to the reporter"
2. Update any user-facing docs that imply reports is one-way
3. Consider adding a `reports_strict` edge type (or a per-edge `bidirectional: false` flag) for users who want strict org-chart enforcement

## Cycle 6 — Delegation depth limit enforcement

**Status:** ✅ Refactor + 12 regression tests. 0 new bugs. The depth enforcement is genuinely solid.

### Architecture finding (benign) — two call sites, same arithmetic

Before this cycle the depth check lived as inline `depth > MAX_DELEGATION_DEPTH` expressions at two places in `flowDelegation.ts`:

1. **Top-level throw path** at line 664-667 inside `executeDelegation` — rejects the call with `DelegationDepthExceededError` before any DB work.
2. **Sub-delegation graceful-refusal path** at line 1058-1066 inside the recursive child-delegation loop — when a child bot wants to recurse one level deeper and the next hop would bust the limit, it appends `[sub-delegation to X refused: depth N > max M]` as an annotation on the parent response instead of throwing. Keeps the parent's reply usable.

Both sites use strict `>` (not `>=`), so with `MAX_DELEGATION_DEPTH = 4` the chain can reach depths `0..4` (entry + four hops) and depth `5` is the first rejected value. depth=0 is "entry bot before any delegation hop" and is always allowed.

### Refactor: extract pure helpers

To make the depth enforcement testable without DB/exec mocks, I extracted two pure helpers into the service:

```ts
export function wouldExceedDepth(depth: number): boolean {
  return depth > MAX_DELEGATION_DEPTH;
}
export function enforceDelegationDepth(depth: number): void {
  if (wouldExceedDepth(depth)) throw new DelegationDepthExceededError(depth);
}
```

Both call sites updated:
- `executeDelegation` now calls `enforceDelegationDepth(depth)` directly (top-level throw path)
- Sub-delegation path now calls `wouldExceedDepth(depth + 1)` (graceful refusal path)

**Zero behavioral change.** The arithmetic is identical; the refactor only moves the check into a named function so it's reachable from unit tests. Both helpers are pure — no I/O, no DB, no `MAX_DELEGATION_DEPTH` closure surprise since the const is computed once at module load anyway.

### Tests added (12 new, 65 total in flowDelegation.test.ts)

New describe block `delegation depth limit (Cycle 6)`:

1. *has a sane default max depth (4 unless env override)* — guards against accidental default bumps
2. *wouldExceedDepth passes for depth = 0 (entry before any hop)*
3. *wouldExceedDepth passes for depth = 1 (first delegation hop)*
4. *wouldExceedDepth passes at the boundary (depth === MAX)* — strict `>` regression guard
5. *wouldExceedDepth fails one past the boundary (depth === MAX + 1)*
6. *wouldExceedDepth fails for arbitrarily deep chains* (MAX + 10, depth=100)
7. *enforceDelegationDepth allows depth 0..MAX without throwing* — loop assertion
8. *enforceDelegationDepth throws DelegationDepthExceededError at MAX + 1* — contract
9. *enforceDelegationDepth preserves the attempted depth on the thrown error* — `err.depth` and `err.maxDepth` field check
10. *thrown error message mentions attempted depth and max — no raw exec leak* — **error sanitization invariant** (must not leak `npx openclaw`/`kubectl`/`exec command`)

## Cycle 7 — Cycle detection in delegation

**Status:** ✅ Refactor + 15 unit tests. 0 functional bugs. 1 minor defensive improvement (defensive array copy on error payload).

### Refactor: pure helpers

Extracted two helpers mirroring the Cycle 6 depth helpers:

```ts
export function wouldCreateCycle(
  ancestors: readonly string[],
  targetDeploymentId: string,
): boolean {
  return ancestors.includes(targetDeploymentId);
}

export function enforceNoCycle(
  ancestors: readonly string[],
  targetDeploymentId: string,
): void {
  if (wouldCreateCycle(ancestors, targetDeploymentId)) {
    throw new DelegationCycleError([...ancestors], targetDeploymentId);
  }
}
```

Both call sites updated:
- `executeDelegation` now calls `enforceNoCycle(ancestors, params.targetDeploymentId)` at line 669
- Sub-delegation path now calls `wouldCreateCycle(nextAncestors, tool.targetDeploymentId)` at line 1049

### Defensive improvement — error payload is now a snapshot

The old code passed `ancestors` directly into the `DelegationCycleError` constructor, which stored a reference (not a copy). In practice no caller mutated the ancestors array after throwing, so this was a dormant footgun. The new `enforceNoCycle` explicitly does `[...ancestors]` so the error payload is a point-in-time snapshot. Pinned by a test called *enforceNoCycle snapshots the ancestors list (mutating it later is safe)* which mutates the caller's array after the throw and asserts the error's `.chain` stays intact.

This is a zero-risk defensive improvement. If a future change introduces a mutable ancestors pattern, the error payload stays correct.

### P2 — FIXED — Synthesis prompt sees empty body when specialist produces only blocks

**Root cause found at `flowChat.ts:716`.** The synthesis prompt is built from `delegationTrace.filter((d) => d.success).map((d) => "[BEGIN ${slug} FULL REPLY]\n${d.fullResponse}\n[END ${slug} FULL REPLY]")`. `d.fullResponse` is the parsed text from the specialist — when a specialist emits `jarble_ui` blocks with **no preamble text**, `fullResponse` is empty and the synthesis prompt becomes:

**Fix applied**:
1. Added `blockTypes: string[]` to `DelegationTraceEntry` interface at `flowChat.ts:166`

```
[BEGIN specialist FULL REPLY]
(no text reply; rendered 2 UI components: stat_grid, data_table — the user has already seen them streamed above)
```

### P2 UX/security finding — bots see `[DELEGATION_CONTEXT]` wrapper and flag it as prompt injection

Discovered while trying to force the blocks-only path. The second test's specialist reply started:

> "I notice something important here that I want to be transparent about. The `[DELEGATION_CONTEXT]` block in your message — along with content injected into `SOUL.md` — appears to be a..."

(183 chars, truncated mid-sentence in the capture but clearly heading toward "prompt injection attempt")

**Root cause at `flowDelegation.ts:887`**: the delegation wrapper is literally injected into the user message:

```ts
message = `[CANVAS_STATE]\nNo cards on canvas.\n[/CANVAS_STATE]\n[DELEGATION_CONTEXT]\nYou are being delegated a task by a coordinator bot. Render your response as jarble_ui components.\n...rules...\n[/DELEGATION_CONTEXT]\n${message}`;
```

The specialist bot sees this wrapper as raw input and a cautious model correctly flags it as "wait, something is injecting content into my context". It then refuses to use `render_ui` — even though the tool IS available — and instead writes a polite "I can't do this because the environment looks suspicious" refusal. **The first test worked because the user prompt didn't set off the model's injection-detection heuristics.** The second test's aggressive "DO NOT write ANY text" phrasing matched patterns the model is trained to resist.

**Why this is a finding and not a bug**: the wrapper does its job — the FIRST test specialist happily followed the rendering rules. But the wrapper is FRAGILE:
- Chatty models can expose the internal plumbing to users by quoting it
- Aggressive task phrasing triggers refusal behavior
- Future model updates might make more models flag it
- Users see cryptic "I notice [DELEGATION_CONTEXT]..." responses without knowing what's happening

**Recommended follow-ups (not code-fixed this cycle)**:
1. Move delegation rules into a proper **system prompt** via OpenClaw / MCP protocol rather than wrapping the user turn. Most LLMs trust system-role instructions and don't surface them to users.
2. Or rename the wrapper to a tag name LLMs don't associate with injection patterns (e.g., `<flow_rules>` instead of `[DELEGATION_CONTEXT]` which sounds like a user-facing term).
3. Add a log-metric that counts specialist replies containing literal `[DELEGATION_CONTEXT]` so the pattern is monitored.

Logged in the running report. This is a medium-priority improvement but blocking it on Cycle 9 would force a multi-file refactor of the delegation/exec path.

## Cycle 10 — Active team selection persistence

**Status:** ✅ **2 P1 stale-reference bugs FOUND and FIXED**, both reproduced live in prod against the pre-fix code, typecheck clean. No new unit tests (mutations hit DB heavily; fix validated via live API reproduction).

### The two bugs

`deployments.activeFlowId` is a plain `varchar(255)` column at `schema.pg.ts:94` with **no foreign key** to `orchestration_flows.id`. That's a fine schema choice but it means writes to the flow table need to explicitly clean up dangling references. Neither of the two flow-mutating paths did.

**Bug 1 — `flows.delete` leaves stale activeFlowId.** Both hard delete (`db.delete(orchestrationFlows)`) and soft delete (archive + strip memberships) update the flow row and the join table but never touch `deployments.activeFlowId`. After deletion, a deployment that had this flow as its active team retains the dangling ID forever.

**Bug 2 — `flows.update` leaves stale activeFlowId on removed members.** When a user edits a flow to drop a node, `syncFlowMemberships` wipes and re-inserts the `flow_deployment_memberships` rows. The removed deployment's membership row is gone, but its `activeFlowId` still points at the flow it was just removed from.

### Silent runtime consequence

At `tamboAgent.ts:1118-1121`:
```ts
const activeFlowId = deployment.activeFlowId;
const membership = (activeFlowId
  ? memberships.find((m) => m.flowId === activeFlowId)
  : null) || memberships[0];
```

When `activeFlowId` is stale, `find(...)` returns `undefined` and the `||` falls through to `memberships[0]` — whichever team happens to be first in the user's membership list. **Silent mis-routing**: the UI can show "active team: Engineering Squad" while the bot actually delegates via "Marketing Squad". Breaks the contract that `setActiveFlow` persists a specific choice.

## Cycle 11 — Team Chat panel in canvas

**Status:** ✅ **3 duplicate regex sites consolidated + 3 holes plugged** in a shared helper. 24 new frontend unit tests. Typecheck clean.

### The audit

The Team Chat panel in the Bot Teams canvas renders inline chat bubbles via the raw `msg.content` string. I traced the code and found **three separate inline delegation-block transform implementations** in the frontend, each with the same regex pattern and the same three latent bugs:

1. `Jarble-mvp/components/MarkdownMessage.tsx:10-23` — per-deployment chat (blockquote format)
2. `Jarble-mvp/views/Deployments.tsx:4069-4072` — Team Chat panel in canvas (inline format)
3. `Jarble-mvp/components/workspace/ConversationHistoryPanel.tsx:34-40` — sidebar preview (strip entirely)

All three used variants of:
```ts
.replace(/```jarble_delegate\s*\n\s*\{[^}]*"to"\s*:\s*"([^"]+)"[^}]*"task"\s*:\s*"([^"]*)"[^}]*\}\s*\n?```/g, ...)
```

### The three holes in the old regex

**Hole 1 — field order dependency**: the regex requires `"to"` to appear before `"task"`. LLMs **do not** guarantee JSON field order. If the specialist emits `{"task":"...","to":"..."}`, the match fails and the raw fenced JSON leaks to the user. I caught this exact pattern in live testing during Cycles 4–9 on intermittent turns.

**Hole 2 — braces inside the task string**: `[^}]*` between fields cannot match `}`, so a task containing `"render {foo: bar} as a card"` breaks the match. Any bot asked to produce code/JSON snippets via delegation is a candidate for this failure mode.

**Hole 3 — escaped quotes inside the task string**: `"([^"]*)"` stops at the first literal `"`, so a task containing `"Say \"hello\" in French"` breaks the match. Escaped quotes are common in natural-language tasks.

All three holes have the same failure signature: **the raw fenced JSON leaks verbatim into the user's chat bubble**. The per-turn probability is low (LLMs often happen to use "to" first and keep tasks brace-free), but it's non-zero and degrades trust.

### Fix — shared helper using proper JSON parsing

Created `Jarble-mvp/lib/delegationBlockTransform.ts` with three exported functions:

| Export | Purpose |
|---|---|
| `parseDelegationBody(body: string)` | `JSON.parse` the fenced body and return `{to, task, context?}` or null. Handles both `{to, task}` and legacy `{tool: "delegate_to_X", task}` formats. |
| `transformDelegationBlocks(text, {format, maxTaskChars})` | Replace each fenced block with human-readable text. `format: "blockquote"` (Markdown `>`) or `"inline"` (plain). Malformed blocks are silently stripped (never leaked). |
| `stripDelegationBlocks(text)` | Replace each fenced block with empty string. Used by the conversation sidebar where delegation mechanics shouldn't appear at all. |

The key change: the outer-fence regex captures only `` ```jarble_delegate\n(.*?)\n``` ``, and then the body is **parsed as JSON** rather than extracted via regex. Field order is irrelevant. Braces and escaped quotes work. The fail-safe is "strip silently" rather than "leak raw" — users still see delegation status pills via `delegation.start/end` SSE events on a separate channel, so nothing is actually lost.

### T4 — nested error bubbling

The self-reference test produced this exact error chain:

> `Subflow failed: Node "selfRef": Subflow failed: Node "selfRef": Subflow failed: Node "selfRef": Subflow nesting depth exceeded: max 3 levels allowed`

Reading this from right to left:
1. **Depth 3** entered `executeSubflowNode` for `selfRef` → `this.nestingDepth + 1 > 3` = `3 + 1 > 3` = true → throws `"Subflow nesting depth exceeded: max 3 levels allowed"`
2. **Depth 2** caught in `executeStep` catch → marked `selfRef` at depth 2 as `failed` with prefix `Node "selfRef": <child error>` → `execute()` returns `status: failed`
3. **Depth 2's parent (depth 1's executeSubflowNode)** caught via `if (childState.status === "failed")` → threw `"Subflow failed: <child error>"`
4. **Depth 1** caught in its executeStep → marked → returned failed
5. **Depth 0's executeSubflowNode** caught → threw `"Subflow failed: Node \"selfRef\": Subflow failed: ..."` — the nested wrapping we see in the final message

Each bubble-up level adds **two prefixes**: `Subflow failed:` from `executeSubflowNode` and `Node "selfRef":` from `executeStep`'s error-handling branch. For a 3-level recursion this produces 3 repetitions of the `Subflow failed: Node "selfRef":` pattern before the root cause. Verbose but accurate.

**Design observation** (not a bug): the nested prefixes could be flatter. A cleaner pattern would be to catch `Subflow failed:` in the outer executeSubflowNode and NOT re-wrap it, since the prefix is already present from the inner wrap. Not critical — users effectively never hit nesting depth limits in practice.

### P2 — FIXED — Unhandled rejection warning in `finally` chain

**Found by the test battery, not by reading the code.** The original implementation at both sites used:

```ts
const next = prev.then(fn, fn);
sessionExecLocks.set(sessionKey, next);
next.finally(() => { if (get(key) === next) delete(key); });  // ← discarded promise
return next;
```

When `fn` throws, `next` rejects. The caller observes the rejection via `return next`, so their branch is handled. **But `next.finally(...)` creates a SECOND observation branch** — the finally-wrapped promise inherits the rejection (finally rethrows), and that branch is DISCARDED without a handler. Node tracks rejection handling per-branch, so the finally branch fires Node's `unhandledRejection` event on every failed chat call.

I caught this because Vitest flagged "4 unhandled rejections" while all 12 tests **passed**. The tests exercised error paths (`fn` throws `"A failed"`, `"err1"`, `"err2"`, `"sync boom"`) and each failing call emitted an unhandled rejection warning even though `await expect(p).rejects.toThrow(...)` correctly consumed the caller-side rejection. The finally side was orphaned.

In prod this would trigger `process.on('unhandledRejection', ...)` handlers (if wired for metrics/logging) on every chat turn that throws. Not catastrophic, but noisy and misleading when debugging.

**Fix at `sessionLock.ts:53-62`**:
```ts
void next
  .finally(() => { /* cleanup */ })
  .catch(() => {
    // Swallow — the caller already observes the rejection through
    // the returned promise. We only want the finally side-effect to run.
  });
```

The trailing `.catch(() => {})` terminates the finally-wrapped branch with a no-op handler. `void` makes the discard explicit. Zero behavioral change on success cases; rejection cleanup still runs; Node no longer fires unhandled rejection.

Post-fix re-run: **12 tests pass, 0 unhandled rejections**.

### P0-A — FIXED (`e84454f`) — Raw `401 Missing Authentication header` in Dev chat

**Root cause**: `chatViaExec` at `openclawGateway.ts:920` extracts `payloads[].text` from OpenClaw's JSON response and treats any non-empty string as a valid bot reply. When OpenClaw's upstream LLM call fails (bad API key, provider 4xx), OpenClaw surfaces the provider's error as a pseudo-text payload — so a string like `"401 Missing Authentication header"` flows through as:
1. Streamed `TEXT_MESSAGE_CONTENT` delta to the user (chat bubble)
2. Stored in `chat_messages` via `tamboAgent.ts:1778` persistence
3. Rendered forever in conversation history on reload

From the user's perspective the bot appears to have said `"401 Missing Authentication header"`. The Cycle 1 visit to the Dev deployment captured this exact text as three consecutive assistant messages. Prior agent memory (Apr 4, Apr 8) had flagged the same pattern but in a different code path (`flows.generateFromPrompt`) — this fix closes the chat path.

**Fix strategy**: detect error-shaped replies at the lowest layer (`chatViaExec`) and **throw** so the caller's existing catch branch runs. Every consumer benefits — direct chat via `tamboAgent.ts:1817` already routes exceptions through `classifyError()` → user-friendly suggestion, and flow chat via `flowChat.ts:525` now uses `sanitizeDelegationError` (Cycle 8).

**New pure helper**: `jarble-api-main/src/utils/botResponseErrorShape.ts`
```ts
isErrorShapedBotReply(text: unknown): boolean
```
- 200-char overall length cap (legitimate HTTP-code explanations get through)
- Anchored prefix patterns: HTTP status + short phrase, `Error:`/`TypeError:`/`RangeError:`/`SyntaxError:`/`ReferenceError:`, bare auth-failure phrases (`Missing Authentication`, `Invalid API key`, `Unauthorized`, `Forbidden`), upstream LLM shapes (`API request failed`, `LLM API error`)
- Per-pattern internal length limit (150 chars for HTTP status phrases) to avoid false positives
- Returns `false` on null/undefined/non-string/empty/whitespace
- **Conservative-by-design**: false negatives are preferred over false positives — a legitimate bot response misclassified as an error would make the bot look permanently broken to the user

**Wired into**: `openclawGateway.ts:922` — the error-shape check fires immediately after `rawText` is extracted and before any downstream processing. Throws `"Upstream LLM error: <preview>"` which the caller's catch branch routes through `classifyError()`.

**17 unit tests** in `botResponseErrorShape.test.ts`:
- 8 positive cases including the exact Cycle 1 string, all common HTTP statuses, JS Error prototypes, bare auth phrases, upstream LLM error shapes, and trailing-whitespace tolerance
- 9 negative cases including prose explaining HTTP codes, responses starting with numbers (dollars, years, answers), long explanations over 200 chars, empty/null/undefined/non-string inputs, normal conversational replies, prose mentioning "error", and lowercase-word-after-number (to distinguish "401 is a status code" from "401 Missing Authentication header")
- 2 boundary cases pinning the 200-char overall cap and the internal 150-char HTTP-phrase cap

All 17 tests pass first try after a single iteration (the first run hit an intentional test-design issue with a 195-char synthetic HTTP phrase that correctly got rejected by the per-pattern cap — fixed the test, not the helper). Typecheck clean on API.

### C9-F — FIXED (`aa4a483`) — `[DELEGATION_CONTEXT]` wrapper rewritten as natural prose

**Cycle 9 finding**: the `[CANVAS_STATE]...[/CANVAS_STATE]\n[DELEGATION_CONTEXT]...[/DELEGATION_CONTEXT]` wrapper injected around delegated task messages at `flowDelegation.ts:887` was triggering prompt-injection-detection heuristics on cautious LLMs. The Cycle 9 "SilentRenderer" adversarial test reproduced this live: the bot quoted the bracketed wrapper back at the user and refused to use `render_ui`, writing `"I notice something important here that I want to be transparent about. **Fix strategy**: rewrite the delegation guidance as natural prose. Drop the CAPS-bracket markers around the rules content. Keep `[CANVAS_STATE]` because it's a FUNCTIONAL marker the bot's system prompt (`JARBLE_UI_PROMPT`) and memory-scope injector (`memoryScope.ts`) look for as trusted dashboard state.

**Rewrite**: the delegation guidance now reads as a single conversational paragraph starting *"You are operating as a specialist within a multi-agent team and have received a delegated task from a coordinator bot..."* — followed by the same rendering rules (prefer stat_grid/data_table/chart/metric_card over sandbox, use recharts format, one component per task, realistic data, layout_hint) expressed as a flowing sentence rather than a bulleted CAPS-RULES list. The sub-team roster (if present) is integrated as a natural paragraph mentioning the delegate block format. The task itself is prefixed with `"Task from the coordinator:"` — a plain label, no markers.

Also **kept the defensive user-input sanitizers** at `flowChat.ts:204` and `tamboAgent.ts:753` that strip `[DELEGATION_CONTEXT]` / `[CANVAS_STATE]` tags from user turns. ### C5-F — FIXED (`2a7f4ab`) — Hover tooltips on flow edge labels

**Cycle 5 finding**: `reports` edges are behaviorally identical to `collaborates` in `buildDelegationTools` — both produce mutual `{A→B, B→A}` tool pairs. The amber dashed directional arrow in the canvas implies one-way delegation, but the engine makes both ends delegate. Users wiring an audit-bot-style one-way reporting relationship will be surprised when the "manager" bot can also initiate tasks downward.

**Fix strategy**: cheapest of the three recommended Cycle 5 follow-ups — hover tooltip on the edge-label pill that surfaces the semantics at the point of decision (when the user hovers over an existing edge or picks a type from the dropdown).

**Implementation at `Deployments.tsx:1394`**: wrapped the edge-label button in shadcn's `Tooltip` (already globally provided by `app/providers.tsx:138`) with per-type content:

- **delegates** — *"One-way delegation. The source bot can send tasks to the target bot. The target cannot initiate delegation back."*
- **reports** — *"Bidirectional reporting relationship. Despite the one-way arrow, BOTH ends can delegate to each other — the reporter can send information up AND the manager can delegate tasks down. If you need strict one-way delegation, use 'delegates' instead."*
- **collaborates** — *"Bidirectional collaboration. Both bots can delegate tasks to each other. Useful for peer-to-peer workflows."*

The `reports` tooltip is the load-bearing one — it solves the UX gap by making the bidirectional behavior discoverable AND suggests the right alternative (`delegates`) for users who need strict one-way semantics. Zero runtime behavior change — purely informational UI.

**Deferred follow-up**: a `reports_strict` edge type that would enforce one-way delegation at the engine level. That's a separate schema change requiring migration, Zod enum extension, test updates, and `buildDelegationTools` branching. Not in scope for C5-F — the tooltip handles 95% of the surprise-avoidance at 5% of the effort.

Frontend typecheck clean. No new tests (pure UI addition with no logic to unit-test; visual regression would be the right test dimension here but visual-regression infrastructure isn't wired up).
