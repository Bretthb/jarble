# K8s & PVC Architecture

## Cluster Overview
- **Platform**: K3s on Hetzner (local dev uses same K3s via kubeconfig)
- **Namespace**: `jarble`
- **Storage**: Longhorn (RWO, 20Gi default per deployment)
- **Container image**: `ghcr.io/jarble-ai/openclaw:latest`

## K8s Resources Per Deployment

Each deployment creates 4 K8s resources:

### 1. Deployment (`dep-{deploymentId}`)
- 1 replica, container name: `runtime`
- Image: `ghcr.io/jarble-ai/openclaw:latest`
- Mounts PVC at `/data`
- Env vars from Secret (`secret-{deploymentId}`)
- Port 18789 (OpenClaw gateway)

### 2. Secret (`secret-{deploymentId}`)
Base entries (always present):
```
DEPLOYMENT_ID, USER_ID, DEPLOYMENT_NAME, TEMPLATE, RUNTIME
```
LLM entries:
```
ANTHROPIC_API_KEY (or OPENROUTER_API_KEY / OPENAI_API_KEY / GOOGLE_API_KEY)
LLM_PROVIDER, LLM_MODEL
```
Platform entries (added by configSync when credentials saved):
```
TELEGRAM_BOT_TOKEN
DISCORD_BOT_TOKEN
SLACK_BOT_TOKEN, SLACK_APP_TOKEN
```
Auto-generated:
```
OPENCLAW_GATEWAY_TOKEN
```

### 3. PVC (`pvc-{deploymentId}`)
- StorageClass: `longhorn`
- Size: 20Gi (configurable per runtime catalog)
- Access: ReadWriteOnce

### 4. Service (if applicable)
- ClusterIP service for inter-pod communication

## PVC Directory Structure (`/data/`)

```
/data/
├── .initialized          # Marker — skips npm install on subsequent boots
├── .npm/                 # npm cache (source of ENOTEMPTY corruption)
│   ├── _cacache/         # Content-addressable cache
│   ├── _npx/             # npx package cache
│   └── _logs/            # npm debug logs
├── .openclaw/            # OpenClaw's own state directory
│   ├── openclaw.json     # OpenClaw native config (generated by entrypoint)
│   ├── .openclaw/        # Internal state (auth store, canvas, sessions)
│   │   ├── auth/         # Pairing auth store (approved senders)
│   │   ├── canvas/       # Web canvas static files
│   │   └── conversations/ # Conversation history DB
│   └── workspace/        # OpenClaw workspace
├── config/               # Jarble platform-managed configs (written by configSync)
│   ├── openclaw.json     # Channel config rendered from DB
│   └── soul.md           # System prompt from DB
├── logs/                 # Application logs
└── runtime/              # npm-installed OpenClaw package
    ├── node_modules/     # ~429 packages
    └── package.json      # Generated by entrypoint
```

## Config Path Architecture (IMPORTANT)

There are TWO openclaw.json files with different purposes:

| Path | Written By | Read By | Contents |
|------|-----------|---------|----------|
| `/data/config/openclaw.json` | configSync (Jarble API) | File watcher → API callback | Channel configs, agent model |
| `/data/.openclaw/openclaw.json` | OpenClaw entrypoint | OpenClaw gateway | Native config (model, gateway port) |

**Key insight**: OpenClaw reads platform tokens (Telegram, Discord, Slack) from **environment variables** (K8s Secret), NOT from either openclaw.json file. The openclaw.json channels config enables/disables channels and sets policies (dmPolicy), but the actual tokens come from env vars.

## ConfigSync Pipeline (DB → Pod)

Triggered by: `void syncConfigsToPvc(deploymentId)` (fire-and-forget)

```
1. Load deployment + platformCredentials from DB
2. Check deployment status (wait up to 120s for "creating" → "running")
3. Check pod status via K8s API (must be "running")
4. Get runtime handler (e.g., openclawHandler)
5. Build DeploymentFields → renderConfigs() + getSecretEntries()
6. writeConfigsToPvc() — exec into pod, write files via stdin stream
7. updateDeploymentSecret() — replace K8s Secret with full entry set
8. Set DB status to "creating" (frontend shows spinner)
9. restartDeployment() — scale 0 → 1
10. Poll for pod readiness (30 attempts × 2s = 60s)
11. Set DB status to "running" or "failed"
```

### ConfigSync Triggers
- `platformCredentials.save` mutation (always fires)
- `platformCredentials.delete` mutation (only if deployment is "running")
- `platformCredentials.markWhatsAppConnected` mutation (only if "running")
- Initial deployment creation (writes initial configs in deployment.create)

## Pod Entrypoint Flow

```
1. Check /data/.initialized marker
2. If first boot:
   a. Create /data/runtime/package.json
   b. npm install openclaw@latest (slow, 2-3 min)
   c. Generate default soul.md and openclaw.json
   d. Create .initialized marker
3. Start file watcher (watches /data/config/, callbacks to API)
4. Run `npx openclaw` (starts gateway on port 18789)
5. OpenClaw doctor runs, auto-enables channels based on env vars
6. Gateway starts, registers Telegram/Discord/etc. providers
```

## Pairing Flow (Telegram)

```
1. User enters bot token in wizard → validated via Telegram getMe API
2. Credentials saved to DB → configSync writes to PVC + updates Secret
3. Pod restarts → OpenClaw detects TELEGRAM_BOT_TOKEN → enables Telegram
4. User messages bot on Telegram → OpenClaw sends pairing code
5. Frontend polls pollTelegramPairing every 3s
6. Backend execs into pod: `npx openclaw pairing list telegram --json`
7. Finds pending request → `npx openclaw pairing approve telegram {code} --notify`
8. Bot confirms pairing, user can now chat
```
